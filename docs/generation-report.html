¿Cuánto tardó?

No existe un cronómetro global exacto asociado a toda la conversación, por lo que no sería correcto afirmar un tiempo total al segundo. Sí hay una ventana verificable en GitHub Actions para la fase final: los trabajos de CI, correcciones de tests, aumento de cobertura y merge a main se desarrollaron aproximadamente entre las 21:32 y las 21:43 del 17 de septiembre de 2026.

Por tanto, la parte observable y medible de estabilización y publicación duró aproximadamente 10–15 minutos. La generación inicial del código ocurrió antes de esa ventana, así que el tiempo total real fue algo mayor.

Importante: esta cifra es una estimación basada en timestamps de commits y GitHub Actions, no un tiempo de CPU ni una medición exacta de principio a fin.

Qué se generó

  • Microservicio Spring Boot con Java 21 y Maven Wrapper.
  • Contrato OpenAPI como fuente de verdad, con generación de interfaces de servidor.
  • CRUD y búsqueda de entrenamientos y zapatillas de running.
  • Modelo detallado de entrenamientos: segmentos, laps, trackpoints, métricas de ritmo, pulso, potencia, cadencia, elevación y condiciones ambientales.
  • Persistencia JPA sobre SQL Server con Flyway y ddl-auto=validate.
  • Dockerfile multi-stage y compose.yaml con SQL Server y volumen persistente.
  • Mappers, capa de servicio, repositorios, controladores y manejo centralizado de errores.
  • Tests unitarios, tests de controladores, Cucumber y JaCoCo.
  • Workflow de GitHub Actions con gates de compilación y cobertura.

Incidencias que ayudaron a mejorar el proyecto

El CI fue útil para detectar problemas que una generación puramente estática no habría demostrado. Primero, Cucumber compilaba pero no podía arrancar por falta de configuración de contexto. Después de resolverlo, el build llegó a JaCoCo y mostró una cobertura del 12%, claramente insuficiente para la regla del proyecto.

En lugar de bajar el umbral, se incrementó la cobertura con tests adicionales. Durante esa ampliación también aparecieron errores de tipos en los tests —se estaban utilizando literales Long en propiedades declaradas como Integer—, que fueron corregidos antes de la ejecución final.

Gate final de calidad

El criterio de publicación quedó definido de forma simple: el microservicio puede llegar a main si compila y mvn verify termina correctamente, incluyendo los tests y el check de JaCoCo con al menos un 80% de cobertura de líneas del código de aplicación.
